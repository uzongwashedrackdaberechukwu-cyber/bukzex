BUKZEX — PROJECT HANDOVER / CLIENT IMPLEMENTATION GUIDE
=============================================================

Purpose
-------
This document explains what has been completed on the BukzEx website, how the current system works, what is still required from the client, and how the project should be taken from the current frontend/demo stage to a fully operational production platform.

The project is intentionally kept simple and professional so that the final API/backend integration can be added without unnecessary complexity.


1. WHAT BUKZEX IS
-----------------

BukzEx is a multi-service digital platform with these six services:

1. VTU
2. Marketplace
3. Virtual SMS / OTP
4. Social Media Boost
5. Gift Cards
6. Crypto

The public website introduces the platform and its services.

Customers can create an account, log in, fund their wallet, purchase services, view orders, manage their profile and access settings.

Administrators have a separate administration panel using the same login page. The system automatically sends the user to the correct dashboard based on their role.

FUND WALLET FLOW
----------------

The current demo wallet flow is:

1. Customer logs in.
2. Customer opens Fund Wallet.
3. Customer sees the configured bank transfer information.
4. Customer enters the amount.
5. Customer completes the transfer through the bank/payment provider.
6. Customer enters the transfer reference.
7. Customer submits the deposit.
8. Deposit is stored as pending.
9. Admin can see the pending deposit.
10. In demo mode, the admin can confirm the deposit.
11. The demo wallet is then credited.

TRANSFER REFERENCE
------------------

The transfer reference is the transaction identifier supplied by the bank/payment provider after the customer makes the transfer.

The customer should not invent a reference.

6. ENVIRONMENT VARIABLES
------------------------

When the production API is ready, the frontend will use an environment variable similar to:

VITE_API_BASE_URL=https://YOUR-API-DOMAIN.com

This should be configured in the hosting provider's environment-variable settings.

Do not put private backend secrets in the React frontend.

Anything beginning with VITE_ is exposed to the browser after the application is built.

Therefore:

SAFE FOR FRONTEND:
- Public API base URL
- Public configuration values

DO NOT PUT IN FRONTEND:
- API secret keys
- Payment secret keys
- Database passwords
- Private service-provider credentials
- JWT signing secrets
- Supabase service-role keys
- Private encryption keys


7. PRODUCTION BACKEND RESPONSIBILITIES
--------------------------------------

The backend must be authoritative for:

- Authentication
- Authorization
- User roles
- Wallet balances
- Payment verification
- Deposits
- Transactions
- Service purchases
- Order status
- Provider/API credentials
- Pricing

8. SECURITY REQUIREMENTS
------------------------

Before production launch:

- Replace demo authentication.
- Hash passwords on the backend.
- Use secure session/token handling.
- Never trust wallet balances sent by the browser.
- Never trust payment confirmation from the browser.
- Verify payment server-side.
- Validate all amounts server-side.
- Validate service purchases server-side.
- Prevent duplicate transaction processing.
- Protect admin endpoints with server-side authorization.
- Keep API secrets on the server.
- Configure HTTPS.
- Configure proper CORS.
- Add rate limiting where appropriate.
- Log important financial operations.
- Use database transactions for wallet operations.


9. CURRENT DEMO MODE
--------------------

When VITE_API_BASE_URL is not configured, the frontend operates in demo mode.

This allows the client to demonstrate the interface without the production API.

Demo data is stored in browser localStorage.

This means:

- Data belongs to the current browser/device.
- Data is not a shared production database.
- Clearing browser storage can remove demo data.
- Another device will not automatically see the same demo data.
- Demo wallet confirmation is not real payment verification.

This distinction must be understood before showing the platform as a live financial/service platform.

13. IMPORTANT API INTEGRATION NOTE
---------------------------------

The current frontend already has a service abstraction in:

src/services/api.js

This is intentional.

Instead of putting API calls directly throughout every React component, the application can be connected to the client's backend mainly through this service layer.

The future process should therefore be:

Frontend UI
    ↓
src/services/api.js
    ↓
Production API
    ↓
Database / payment provider / service providers


This keeps the UI easier to maintain.

15. WHAT THE CLIENT SHOULD NOT DO
---------------------------------

The client should not:

- Edit the frontend code randomly.
- Put secret API keys inside React components.
- Put payment secret keys in VITE_ variables.
- Manually credit customer wallets in production.
- Trust a browser confirmation button for payments.
- Treat localStorage as the production database.
- Use the demo admin password in production.
- Assume a successful frontend response means a real transaction succeeded.

18. HANDOVER SUMMARY
--------------------

The BukzEx frontend is currently a functional, responsive application with a complete customer-facing flow and a structured administration panel.

The current system intentionally runs in demo mode when no production API is configured.

The next phase is backend/API integration.

The frontend should NOT be considered a live financial transaction system until:

- Authentication is moved to the backend.
- Wallet operations are server-controlled.
- Deposits are actually verified.
- Payment/webhook processing is implemented.
- Service provider APIs are connected.
- Orders are stored in the production database.
- Admin authorization is enforced server-side.
- Production secrets are secured.

Once those pieces are supplied, the existing frontend service layer can be connected to the real backend and the demo/local data layer can be removed or disabled.
